# Технічний аудит HeatingPumpSait

**Дата аудиту:** 4 листопада 2026 року
**Обсяг:** структура, frontend, серверний API, схема PostgreSQL, форма попереднього підбору, конфігурація публікації та доступні перевірки.

## Підсумок

Проєкт містить React 18 + TypeScript + Vite frontend та окремий Express API на TypeScript із Prisma і PostgreSQL. Є міграція бази, схема заявок і адміністраторів, сесійна автентифікація адміністратора та форми. Після змін 4 листопада 2026 року приймання заявок вимкнене за замовчуванням і потребує явного прапорця середовища на frontend та API. Google Analytics, інша вебаналітика й події конверсій не налаштовані.

Production frontend збирається для GitHub Pages із базовим шляхом `/HeatingPumpSite/`. Workflow публікує лише статичний каталог `dist`; він не запускає API й не надає PostgreSQL. API налаштовано окремо, але в репозиторії немає deployment-конфігурації для нього. Локального `server/.env` немає. Через це наявність коду backend не означає, що він зараз доступний для публічного сайту.

## Структура і маршрути

- Frontend: `src/App.tsx`, React-компоненти й секції в `src/components/` та `src/sections/`, вміст у `src/data/`.
- Сервер: `server/src/index.ts`; адміністративний інтерфейс: `src/components/AdminPage.tsx`.
- База: `server/prisma/schema.prisma`; одна початкова міграція `20261023000000_init` створює `Lead`, `AdminUser` та `Session`.
- Основні клієнтські маршрути: головна, `/brands/...`, `/knowledge/...`, `/privacy`, `/admin`. Розбір URL виконується в `src/App.tsx`; Vite задає `base: "/HeatingPumpSite/"`.
- Відомі сторінки брендів та матеріалів обробляються окремо; невідомі шляхи на стороні React показують головну сторінку. Перевірка живих URL на GitHub Pages не проводилася.
- Workflow `.github/workflows/deploy.yml` збирає та публікує лише frontend на кожне оновлення `main`.

## Backend і база даних

API містить:

- `GET /api/v1/health` — перевіряє запит `SELECT 1` до БД і повертає `ok` або `unavailable`.
- `POST /api/v1/leads` — валідує заявку Zod-схемою та створює запис у `Lead`.
- `GET /api/v1/auth/csrf`, `POST /api/v1/auth/login`, `GET /api/v1/auth/me`, `POST /api/v1/auth/logout` — адміністраторська сесія та CSRF-захист.
- `GET /api/v1/admin/leads` — повертає адміністратору до 100 останніх заявок.

У коді присутні Helmet, обмеження частоти для заявок/входу/CSRF, обмеження розміру JSON, Argon2 для паролів, HttpOnly/SameSite cookie та Secure cookie в production. Схема БД має індекси за датою та статусом. Міграція створює таблицю сесій. Це результати огляду коду, не перевірка runtime-конфігурації.

**Стан підключення:** `server/.env` відсутній, тому значення `DATABASE_URL`, `SESSION_SECRET`, production origin та версію політики не перевірено. Запуск міграцій, перевірка фактичного стану схеми, health endpoint і запис/читання контрольної заявки не виконувалися. БД локально не створювалася.

## Форма підбору та збереження заявки

Форма проходить три кроки: населений пункт/площа/тип об’єкта, система опалення/термін, потім ім’я/телефон/згода. Клієнт не розраховує потужність теплового насоса. Перед відправкою формується JSON `source: selection`; контактна форма надсилає `source: contact`. Обидві форми викликають `POST /api/v1/leads`.

Сервер вимагає згоду, перевіряє допустимі значення для полів підбору та формат телефону, нормалізує текст, записує час і версію політики, а клієнту повертає лише ID/дату/статус. Панель `/admin` після входу показує останні заявки.

Стан на 4 листопада 2026 року: frontend за замовчуванням не формує та не надсилає payload заявки, кнопки відправлення вимкнені, а API відповідає `503`, якщо приймання не ввімкнене. `LEADS_ENABLED`/`VITE_LEADS_ENABLED` мають бути явно задані як `true`, щоб увімкнути реальне приймання. Перевірено компіляцію frontend/API та конфігурацію Compose; після цього блокування окремий запуск контейнерів для перевірки 503 ще не виконаний.

Публікація лише на GitHub Pages не забезпечує `/api/v1/leads`. У Vite є проксі `/api` для локального dev-сервера, але це не налаштовує production-маршрутизацію. Отже, реальне збереження заявок із опублікованого сайту не підтверджене й без окремого API hosting/reverse proxy очікувати його не слід.

## Аналітика

У `index.html`, frontend-коді та залежностях не знайдено GA4, gtag, GTM, Plausible чи іншого трекера. Подій перегляду сторінки, початку форми, кроків і успішної заявки немає. Статистику відвідувань зараз збирати нічим.

Рекомендований наступний вибір після узгодження вимог до приватності:

1. **GA4** — якщо потрібні стандартні звіти про джерела трафіку й конверсії та власник погоджує Google Analytics і відповідні повідомлення/налаштування приватності. Події: `page_view`, `selection_start`, `selection_step`, `generate_lead` лише після відповіді API зі статусом успіху. Не передавати ім’я, телефон, коментар, адресу чи параметри, за якими можна ідентифікувати людину.
2. **Plausible або Matomo** — розглянути як альтернативу, якщо потрібна мінімальніша аналітика чи власне розміщення. Вибір залежить від вимог до згоди, хостингу, зберігання та правового тексту; жоден трекер у межах аудиту не встановлювався.

## Перевірки

- `npm run build` — успішно: TypeScript і Vite production build пройшли. Під час цієї збірки виявлено некоректний CSS-селектор placeholder; виправлено на `input::placeholder, textarea::placeholder`.
- `npm run build:server` — успішно: Prisma Client згенеровано, TypeScript backend скомпільовано.
- `npm test -- --run` — недоступно: у кореневому `package.json` немає script `test`. Відповідного test script у `server/package.json` також немає.
- `npm run db:migrate` — навмисно не запускалося: відсутній `server/.env`, а завдання не передбачає створення БД чи зміну схеми без погодження.
- Перевірка браузером, production API та фактичної БД — не проводилася.

## Ризики та межі готовності

1. **Немає підтвердженого backend hosting/DB connection.** Потрібно визначити, де працюватимуть API і PostgreSQL та як сайт безпечно до них звертатиметься.
2. **Політика конфіденційності.** Чинна погоджена редакція 1.0 розміщена в `docs/PRIVACY_POLICY.md` і на `/privacy`. Версія згоди узгоджена як `POLICY_VERSION=1.0`. Автоматичне видалення заявок після 12 місяців від останнього контакту та ротацію backup до 30 днів реалізовано локально; інструкції перевірки — у `docs/DEPLOY_CP02.md`. Production-розгортання, умови DPA та фактичний backup/restore цим аудитом не підтверджені.
3. **Поточна production публікація статична.** Треба спроєктувати API hosting і HTTPS reverse proxy або обрати сумісну платформу, перш ніж вмикати заявки.
4. **Немає тестового набору.** Схеми, API, помилки й інтеграцію з PostgreSQL не покривають автоматизовані тести.
5. **Аналітика відсутня.** Рішення щодо постачальника, згоди та політики має передувати встановленню трекера.
