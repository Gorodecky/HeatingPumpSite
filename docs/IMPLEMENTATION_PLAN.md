# План реалізації HeatingPumpSait

План складено за результатами аудиту від 4 листопада 2026 року. Політика конфіденційності версії 1.0 остаточно погоджена власником; production-сервіси, DNS і трекери цим планом не змінюються.

## Етап 1. Узгодити дані та hosting

1. Форми та API вимкнені за замовчуванням (`LEADS_ENABLED=false`, `VITE_LEADS_ENABLED=false`).
2. Політика `docs/PRIVACY_POLICY.md` версії 1.0 містить погоджені назву/адресу, ціль без маркетингу, обмеження доступу та строки 12 місяців після останнього контакту і 30 днів для резервних копій.
3. Автоматичне видалення заявок і ротацію backup реалізовано у API та Compose; процедура локальної перевірки наведена в `docs/DEPLOY_CP02.md`.
4. До будь-якого production-ввімкнення окремо перевірити фактичні умови DPA/хостингу, production origin, доступи, backup/restore та міграції. Ці локальні зміни не підтверджують стан production.
5. Поточний GitHub Pages workflow розміщує лише статичний frontend.

**Критерій переходу:** окрема перевірка production-хостингу, DPA, резервного відновлення та потоку даних перед увімкненням заявок.

## Етап 2. Під’єднати та перевірити backend

1. Налаштувати секрети лише в середовищі hosting: `DATABASE_URL`, випадковий `SESSION_SECRET`, `APP_ORIGIN`, `NODE_ENV=production`, `POLICY_VERSION=1.0`. Залишити `LEADS_ENABLED=false` до завершення всіх перевірок.
2. Перевірити HTTPS і reverse proxy, cookie-параметри, CORS/origin-межі й довіру до проксі для обмеження частоти запитів.
3. Перед першим застосуванням міграції звірити migration history та схему на цільовій БД; підготувати backup/відновлення. Застосовувати на production лише після окремого погодження.
4. Перевірити `/api/v1/health`, коректну/некоректну заявку, обмеження частоти, недоступну БД, відсутність публічного доступу до заявок і адміністраторський login/logout.
5. Створити обліковий запис адміністратора через документований `admin:create`, використовувати унікальні облікові дані та мінімально необхідний доступ.
6. Перевірити отримання заявки в `/admin`, відповідність згоди фактичній політиці, роботу резервної копії та відновлення.

## Етап 3. Узгодити UI форм і API

1. Перевірити, що вимкнений стан не передає дані ні при натисканні, ні при submit клавішею Enter; frontend і API мають використовувати узгоджені прапорці.
2. Показувати повідомлення про успіх лише після підтвердженого запису API; при недоступності API давати зрозумілу помилку без ствердження про збереження.
3. Перевірити форму підбору й контактну форму на мобільних/настільних екранах, усі обов’язкові поля, згоду, помилки валідації та повторну відправку.
4. Уточнити порядок згоди: користувач має мати змогу ознайомитися з чинною політикою до надсилання персональних даних.

## Етап 4. Додати автоматизовані перевірки

Після підтвердження обсягу додати тести без використання production БД:

- валідація схем заявок і телефонів;
- позитивний та негативний HTTP-сценарії `POST /api/v1/leads`;
- захист `/api/v1/admin/leads`, CSRF і сесії;
- тести переходів форми та помилок API;
- перевірка production-збірки та базових маршрутів під `/HeatingPumpSite/`.

Для інтеграційного запуску використовувати окрему тестову БД із явним очищенням тестових записів, ніколи не production.

## Етап 5. Аналітика за погодженням

1. Вибрати GA4, Plausible або Matomo після рішення щодо згоди, передачі даних третім сторонам, hosting і тексту політики.
2. Якщо вибрано трекер, задати його ID через конфігурацію середовища; не фіксувати секрети в коді.
3. Узгодити мінімальний перелік подій: перегляд сторінки, початок підбору, проходження кроків, успішне надсилання заявки та помилка API.
4. Не включати персональні поля або вільний текст у назви/параметри подій. Подію конверсії фіксувати тільки після успішної відповіді API.
5. Перевірити події в тестовому середовищі, відсутність персональних даних у payload та узгодженість з політикою.

## Етап 6. Реліз

1. Підготувати окрему гілку для погоджених суттєвих змін.
2. Пройти збірки frontend/backend, автоматизовані тести, перевірки форм, API, адміністрування та аналітики в staging.
3. Зробити резервну копію перед змінами production-схеми.
4. Після приймання розгорнути API, БД і frontend; перевірити health, маршрути, заявки та події конверсій.
5. Задокументувати процедури резервного копіювання, відновлення, обробки звернень та видалення заявок згідно із затвердженою політикою.
