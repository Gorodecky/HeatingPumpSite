# Сповіщення про заявки через Resend

API зберігає заявку та запис черги сповіщень у PostgreSQL однією транзакцією. Фоновий цикл у вже наявному API-контейнері надсилає лист менеджеру; окремий контейнер чи брокер повідомлень не додається. Якщо Resend не налаштований, заявка зберігається, а повідомлення залишається в черзі. Помилки журналюються без полів заявки та секретів.

Для повторів використовується сталий ключ `lead-notification/<ID заявки>`. Resend зберігає ключ ідемпотентності 24 години. Черга зберігає `firstAttemptAt`, виконує до восьми спроб у межах 20 годин від першої спроби, а потім позначає запис `FAILED`, не видаляючи заявку чи запис черги. Старий `PROCESSING` можна забрати повторно після 5 хвилин без lock. Якщо перша спроба була понад 20 годин тому, worker позначить його `FAILED`; якщо минуло 24 години — з кодом `IDEMPOTENCY_WINDOW_EXPIRED`. В обох випадках Resend більше не викликається. Після рестарту API стан черги не втрачається в PostgreSQL; застряглі обробки поновлюються після lease timeout зі сталим ключем, поки не минув безпечний retry window. Успішний запис має статус `SENT`.

## Налаштування

1. У панелі Resend створіть API key з мінімально потрібним доступом для надсилання. Збережіть його одразу в менеджері секретів сервера; не додавайте до Git, образу чи клієнтського frontend.
2. У Resend додайте домен `teplo-tvd.live` та опублікуйте DNS-записи, які покаже панель Resend. Дочекайтеся статусу підтвердження домену у Resend. Не підставляйте адресу відправника до підтвердження.
3. У приватному `deploy.env` задайте:

   ```dotenv
   RESEND_API_KEY=<секретний API key>
   RESEND_FROM_EMAIL=notifications@teplo-tvd.live
   LEAD_NOTIFICATION_EMAIL=tvd05@tvd.vn.ua
   ```

   Відправник `notifications@teplo-tvd.live` можна встановити тільки після підтвердження домену. Не змінюйте `DB_PASSWORD` чи `SESSION_SECRET`. `LEADS_ENABLED` лишається `false`, доки окремо не погоджено приймання реальних заявок.

## Застосування на Hetzner

Спочатку зробіть резервну копію БД і перевірте, що доступна команда `docker compose`. З кореня проєкту на сервері застосуйте окрему адитивну міграцію та оновіть наявні сервіси:

```sh
docker compose --env-file deploy.env run --rm migrate
docker compose --env-file deploy.env up -d --build api web
```

Міграція додає таблицю `LeadNotification`, не змінюючи деструктивно таблицю заявок. Не запускайте `down -v` і не видаляйте PostgreSQL том. Після оновлення перевірте `docker compose --env-file deploy.env ps`, `docker compose --env-file deploy.env logs --since=10m api` та `/api/v1/health`.

## Перевірка

- Без реальних листів: з кореня репозиторію запустіть `npm --prefix server test`. Тести передають mock-функцію замість Resend SDK і перевіряють обидва типи заявок, поля листа, HTML-екранування, помилку провайдера та повтор зі сталим ключем.
- PostgreSQL integration tests: запустіть окремий локальний PostgreSQL, створіть test database із назвою, що закінчується на `_test`, задайте `TEST_DATABASE_URL` і виконайте `npm --prefix server run test:integration`. Скрипт перевіряє loopback-хост і суфікс БД, створює тимчасову схему, застосовує всі Prisma-міграції, запускає API та інтеграційні тести, а потім видаляє тільки цю схему. У тестах Resend завжди mock-ований; production URL не допускається.
- Після окремого погодження тесту доставки увімкніть приймання заявок у приватному `deploy.env` через `LEADS_ENABLED=true`, перезберіть `web` і перезапустіть `api`. Надішліть одну контрольовану заявку через кожну форму та перевірте лист на `tvd05@tvd.vn.ua`; потім перевірте `LeadNotification.status = SENT` за відповідним `leadId`. Цей репозиторій не вмикає приймання автоматично.
- Помилки перевіряйте за безпечним повідомленням `Lead notification delivery failed (<код>).` у журналі API. Детальніше про лист дивіться у панелі Resend. У БД перегляньте тільки технічні колонки `status`, `attempts`, `firstAttemptAt`, `nextAttemptAt`, `sentAt`, `lastErrorCode`, `manualRetryCount` і `lastManualRetryAt`; не виводьте персональні дані в журнали.
- Для перевірки телефону відкрийте сторінку на смартфоні та натисніть номер у футері; для клавіатури сфокусуйте посилання клавішею Tab і активуйте Enter.

## Ручний розгляд `FAILED`

Не обнуляйте `attempts` чи `firstAttemptAt` лише для того, щоб запустити worker повторно. Повтор після 24 годин уже не захищений ключем Resend і може створити дублікат, якщо попередня спроба була прийнята, але API не встигло зберегти `SENT`.

1. Зафіксуйте `leadId`, `lastErrorCode` і `firstAttemptAt`; не копіюйте поля заявки в журнали чи чати.
2. У Resend перевірте історію доставок менеджеру за темою `Нова заявка: … (<leadId>)` і часом спроб. Якщо лист є, не надсилайте його знову; узгодьте позначення запису як `SENT` після звірки.
3. Якщо в історії немає листа і доступна повна історія за весь період спроб, уповноважений оператор може в транзакції змінити лише цей `FAILED` рядок на нову чергу:

   ```sql
   BEGIN;
   UPDATE "LeadNotification"
   SET "status" = 'PENDING',
       "attempts" = 0,
       "firstAttemptAt" = NULL,
       "nextAttemptAt" = NOW(),
       "lockedAt" = NULL,
       "lastErrorCode" = 'MANUAL_RETRY',
       "manualRetryCount" = "manualRetryCount" + 1,
       "lastManualRetryAt" = NOW(),
       "updatedAt" = NOW()
   WHERE "leadId" = '<lead-uuid>'::uuid
     AND "status" = 'FAILED'
   RETURNING "leadId", "status", "attempts", "manualRetryCount";
   -- COMMIT only if exactly one row was returned; otherwise ROLLBACK.
   COMMIT;
   ```

   Перевірте рівно один змінений рядок і новий статус після commit. Умова `status='FAILED'` та унікальний `leadId` захищають від повторного запуску тієї самої ручної команди.
4. Якщо історія Resend неповна, недоступна або результат неоднозначний, залиште рядок `FAILED` і зв’яжіться з менеджером іншим погодженим каналом. Не робіть повторну відправку навмання.

Ручний retry є окремим рішенням оператора після перевірки журналу; це не гарантія абсолютної відсутності дублювання, якщо в Resend немає повної історії або попередній результат невизначений. Не додавайте універсальну кнопку повтору в адмінці без окремої перевірки idempotency та аудиту дій.

## Відкат

Збережіть резервну копію БД. Поверніть попередній код і перебудуйте `api` та `web`, не видаляючи таблицю `LeadNotification` і Docker-томи. Prisma-міграція адитивна, тому стара версія може працювати з додатковою таблицею. Існуючі заявки залишаються в `Lead`; невідправлені записи черги також зберігаються та можуть бути оброблені після повторного розгортання цієї версії. Заявки, створені старою версією під час відкату, не матимуть запису черги, бо попередній код про неї не знає.
