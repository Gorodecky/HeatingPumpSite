# Звіт етапу 2: локальне налаштування backend і PostgreSQL

**Дата:** 4 листопада 2026 року
**Середовище:** локальний macOS, PostgreSQL 16.15 (Homebrew), база `heatingpump` на `127.0.0.1:5432`
**Production, GitHub Pages, віддалені бази, DNS, hosting та аналітика не змінювалися.**

## Виконано

- Перевірено аудит і план реалізації. Початкова міграція оглянута до запуску: створює `LeadStatus`, таблиці `Lead`, `AdminUser`, `Session` та індекси; не містить видалення або очищення даних.
- Перевірено, що PostgreSQL 16.15 слухає лише loopback. До створення цільової БД існували `postgres` і `tvd_store`; база `heatingpump` була відсутня.
- Створено окрему локальну БД `heatingpump`, власник — локальний користувач `vitaliyhorodecky`.
- Створено `server/.env` за зразком. URL вказує тільки на `127.0.0.1:5432/heatingpump`; `SESSION_SECRET` згенеровано локально, файл має права `600` і виключений із Git. Значення секрету до звіту/виводу не потрапляло.
- Успішно застосовано міграцію `20261023000000_init` до локальної БД.
- Backend зібрано, API запущено локально. Vite і backend працювали на `127.0.0.1:5173` і `:3001` для перевірки через форму.
- Під час вимкнення API виявлено повторне закриття PostgreSQL-пулу при надходженні обох сигналів завершення. Додано захист від повторного shutdown; backend повторно зібрано й штатно зупинено без помилки.
- Після перевірок локальні процеси API та Vite зупинено; PostgreSQL лишено в початковому стані роботи. Тестовий рядок збережено в локальній БД для огляду.
- У браузері пройдено всі три кроки форми підбору та відправлено вигадану заявку (`Тест Етап 2`, синтетичний номер `+380000000000`, тестове місто). API повернув підтвердження успіху.
- Read-only запит до БД підтвердив рівно один запис із `source=selection`, тестовими параметрами будинку/опалення, `consentGiven=true` і `policyVersion=2026-10-23`. Контактні значення в цьому звіті не повторюються.

## Перевірки

| Перевірка | Результат |
|---|---|
| `npm --prefix server run db:migrate` | Успішно; застосовано одну початкову міграцію до локальної `heatingpump` |
| `npm --prefix server run build` | Успішно; Prisma Client згенеровано, TypeScript backend скомпільовано |
| `npm run build` | Успішно; TypeScript і Vite production build пройшли |
| `GET /api/v1/health` з доступною БД | `200`, `{"status":"ok"}` |
| Надсилання форми підбору | Успішна відповідь форми та підтверджений запис у БД |
| Некоректний номер у заявці | `400`, повернено помилку поля; заявка не прийнята |
| Некоректний JSON | `400`, `Некоректний JSON.` |
| Список адмін-заявок без сесійного CSRF токена | `403`; вміст заявок не повертається |
| API з тимчасово недоступним DB-портом | health `503`/`unavailable`; спроба запису — `500` із загальним повідомленням без деталей підключення |

Сценарій недоступної БД виконувався окремим тимчасовим процесом на `localhost:3002` з URL на неіснуючий локальний порт; основний PostgreSQL не зупинявся і дані основної БД не змінювалися цим тестом.

## Команди локального запуску

Перед запуском переконайтеся, що локальний PostgreSQL працює, а `server/.env` уже налаштовано. У двох окремих терміналах із кореня проєкту:

```bash
npm --prefix server run dev
```

```bash
npm run dev -- --host 127.0.0.1
```

Локальний сайт: `http://127.0.0.1:5173/HeatingPumpSite/`. API health: `http://127.0.0.1:3001/api/v1/health`.

Міграції для локальної бази:

```bash
npm --prefix server run db:migrate
```

Збірки:

```bash
npm --prefix server run build
npm run build
```

`server/.env` містить локально згенерований секрет; не копіюйте цей файл у звіти, повідомлення чи Git.

## Невирішені питання

1. У двох формах лишився текст «Демонстраційний режим…», хоча код реально надсилає дані до API. Після успішного запиту форма також показує правильне підтвердження збереження, тому повідомлення суперечать одне одному. Його варто узгодити окремим UI-кроком до будь-якого приймання реальних заявок.
2. Політика конфіденційності, згадана в аудиті, є заглушкою. Реальні контакти не надсилати, доки власник не затвердить текст політики та не визначить production hosting/API і відповідального за обробку заявок.
3. У проєкті немає тестового скрипту; у цьому етапі виконані ручні браузерні/API/DB перевірки та збірки, постійний набір автоматизованих тестів не додавався.
4. Успішний локальний запис не доводить доступність API з GitHub Pages. Production залишився без змін і його приймання не виконувалося.
